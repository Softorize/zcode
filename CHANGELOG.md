# Changelog

All notable changes to `zcode` should be documented in this file.

## Unreleased

- Add supply-chain dependency-pin CI gate (`scripts/ci/check_dependency_pin.sh` + `scripts/ci/allowed_dependencies.txt`) that fails builds if `build.zig.zon` grows any dependency not explicitly approved in the allowlist.
- Keyless-sign the release SBOM with cosign (Sigstore OIDC) and publish `sbom.cdx.json.sig` and `sbom.cdx.json.pem` alongside the SBOM for enterprise supply-chain verification.
- Cosign-sign every release binary (Linux x86_64/aarch64, macOS x86_64/aarch64) and publish `.sig` + `.pem` artifacts next to each binary. Windows is not built (the codebase uses POSIX-only APIs); the `install.ps1` shim was removed to stop advertising an unsupported platform.
- Emit SLSA v1.0 level 3 build provenance (`zcode.intoto.jsonl`) for the release binaries via the official `slsa-github-generator` reusable workflow.
- Document verification with `cosign verify-blob` and `slsa-verifier` in `docs/security/VERIFY_RELEASE.md`.
- Auto-updater now verifies cosign signatures on downloaded binaries. Advisory by default (warns if cosign missing); set `ZCODE_UPDATE_REQUIRE_SIGNATURE=1` to fail closed.
- Auto-updater honors `ZCODE_UPDATE_PINNED_VERSION` so enterprise deployments can hold at a specific release.
- Add reproducible-build CI job that builds twice and diffs the binaries, catching embedded timestamps or paths.
- Add `scripts/release/airgap_bundle.sh` and release-workflow step to produce per-platform air-gapped install bundles (binary + `.sig` + `.pem` + SBOM + provenance + install script that verifies offline).
- Add OS keychain backend (`src/core/keychain.zig`) with macOS `security`, Linux `secret-tool`, Windows DPAPI (file-fallback placeholder), and authenticated ChaCha20-Poly1305 file fallback for headless systems.
- New CLI: `zcode keychain set|get|delete|list` for managing provider API keys in the OS keychain.
- Providers resolve API keys in precedence order env var → keychain → config, so operators can provision secrets once in the keychain and skip env-var plumbing.
- Session encryption is ON by default. Keys are auto-generated on first run and stored in the OS keychain under `zcode:__session_key__`; `ZCODE_SESSION_KEY` continues to win when set.
- New CLI: `zcode session rotate-key` generates a fresh session key and stores it in the keychain; prints a fingerprint and warns that old sessions become unreadable.
- Add `privacy_redact_prompt_bodies` config; when true, prompt/response bodies are stripped from the audit log (and from OTel payloads where they flow through the same logger) while metadata stays intact.
- New CLI: `zcode audit verify [path]` walks the HMAC chain of an audit log and reports tamper breaks with the offending line number.
- Document the audit log format, retention, redaction, and verification theory of operation in `docs/security/AUDIT_LOG.md`.
- Add system-level managed-config precedence (`/etc/zcode/managed.toml` on Linux, `/Library/Application Support/zcode/managed.toml` on macOS, `%PROGRAMDATA%\zcode\managed.toml` on Windows) that overrides user config so fleet admins can lock privacy, encryption, and telemetry defaults. Override path via `ZCODE_MANAGED_CONFIG`.
- Add fleet deployment playbooks for Microsoft Intune, Jamf Pro, and Ansible in `docs/fleet/`.
- Add CodeQL workflow (`javascript-typescript` for the VS Code extension, `actions` for the workflow files themselves) running on push, PR, and weekly schedule.
- Add nightly fuzz workflow (`.github/workflows/fuzz.yml`) that runs each `fuzz_tests.zig` module with a configurable time budget (default 15 minutes per target) and uploads crash artifacts on failure.
- Add RBAC role hierarchy (`src/policy/rbac.zig`) with `none < viewer < auditor < editor < owner` and a per-endpoint minimum-role table, ready to enforce once OIDC identities replace the single shared daemon token.
- Add OIDC claim parser (`src/core/oidc.zig`) that validates `iss`/`aud`/`exp` in a compact JWS and extracts `sub` + `role` claims. Signature verification (RS256 + JWKS) is a follow-up; the module doc warns call sites to gate admission with mTLS or a trusted reverse proxy until then.
- Add `src/core/resource_limits.zig` for `setrlimit`-based memory/CPU/FD/proc caps on spawned tool processes (POSIX; Windows Job Object scaffolding pending).
- Add `src/core/egress.zig` central outbound-URL chokepoint combining scheme check, SSRF block-list, and a managed-config allowlist so fleet admins can lock zcode to specific provider endpoints.
- Document the sandbox roadmap (seccomp-bpf + Landlock on Linux, tighter sandbox-exec on macOS, AppContainer + Job Object on Windows) in `docs/security/SANDBOXING.md`.
- Add `.well-known/security.txt` (RFC 9116) pointing at the GitHub private-vulnerability-reporting channel.
- Expand `SECURITY.md` with PGP fingerprint placeholder, CVE/CNA handling note, and links to every security / compliance doc.
- Add SOC2 control mapping, GDPR DPA template, and data-flow diagram in `docs/compliance/`.
- Fix (ultrareview): `zcode session rotate-key` now prints a SHA-256 fingerprint instead of the raw key prefix, and refuses to run when `ZCODE_SESSION_KEY` is set (which would silently shadow the keychain-stored rotation).
- Fix (ultrareview): `zcode audit verify` no longer auto-creates an `hmac.key` when the file is missing; reports "HMAC key missing" distinctly from tampering so forensic copies work.
- Fix (ultrareview): auto-generated session-encryption key MUST now persist successfully; a persist failure aborts startup with a specific error (previously the next run would generate a fresh key and silently make prior sessions undecryptable). Paired with wider file-fallback on any OS-keychain failure so headless / CI / container environments still work.
- Fix (ultrareview): managed config now fails closed on `AccessDenied`; a deployed-but-unreadable `/etc/zcode/managed.toml` aborts startup instead of silently applying the user's config.
- Fix (ultrareview): `zcode providers status` now probes the OS keychain in addition to env + config, so keychain-provisioned keys report `source=keychain` instead of the misleading `configured=false`.
- Fix (ultrareview): cosign-availability probe in the auto-updater uses `cosign --version` directly instead of `sh -c command -v cosign`; the old path always missed on Windows and silently downgraded updates to checksum-only verification.
- Fix (ultrareview): reproducible-build CI now invokes `scripts/release/build_release_asset.sh` twice with the release-matching args (ReleaseSafe + version override) instead of bare `zig build -Doptimize=ReleaseFast`, so the check covers what actually ships.
- Fix (ultrareview): `zcode keychain set <provider> <secret>` rejects stray extra argv tokens instead of silently joining them with spaces into a mangled secret.
- Fix: the "repeated response" loop-breaker in `agent_runtime.zig` no longer disables tools after two text-only rounds with matching signatures (common after plan-mode approval when the model recaps the plan). Disabling tools there would feed the model a "Tools are NOT available" system message and the model would correctly emit a FINAL_NO_ACTION blocker even though tools were always available. The text-only stall path (action-reprompt + protocol-fallback) already handles this case.
- Remove the automatic provider/model fallback switch (`tryProtocolFallback`). When the user picks a model, we stay on it; stalls surface concretely to the user instead of silently hot-swapping to the configured fallback provider. The `fallback_provider*` config keys remain parseable for backward compatibility but are no longer consulted at runtime.
- Local (Ollama) adapter now emits `num_ctx` in the request options when the caller supplies `context_window` via `ModelRequest`, so the configured context window is used explicitly instead of relying on Ollama's VRAM-based default.
- Fix: interrogative prompts ("what is X", "how does Y", "describe Z", etc.) now count as action-requiring for the intent-reprompt heuristic. Previously only imperative verbs triggered the reprompt, so a model that replied with pure narration ("Let me explore the project structure...") to "what is this project about" was accepted as the final answer without ever calling a tool. The old test that codified this behavior was flipped to the correct expectation.
- Fix: `shouldRepromptForToolCalls` now forces a reprompt whenever the assistant reply opens with an unambiguous "promise of action" ("Let me ...", "I'll ...", "I will ...", "I'm going to ...", "Sure, let me ...", etc.) and no tool call is attached, regardless of how the user phrased the request. Catches short-confirmation flows ("ok", "lets login", "go ahead") where the prior user prompt didn't contain imperative cues but the current assistant turn is still a stall.
- Fix: `toolCallsSignature` no longer hashes the assistant narration when tool calls are present, so identical-call loops caught by the loop-breaker even when the model varies "Let me try..." / "I see the issue..." wrapper text round-to-round.
- Remove `ssh`, `telnet`, `ftp` from the always-interactive command list in `bash_security.zig`. zcode's shell tool closes stdin, so an ssh without a command returns EOF and exits cleanly, and ssh with a command runs the remote command non-interactively. Blocking them broke legitimate remote admin flows and produced "sandbox blocking SSH" loops.
- `danger-full-access` sandbox profile now fully bypasses destructive-shell, interactive, and redirect-tool gates in `shell.zig` AND `registry.zig` (both layers honor the opt-in; `validateCommandInput` for empty/null-byte/over-long commands still fires).
- **Fix (data loss)**: `buildDirectPlan` used `&.{"/bin/sh","-c",command}` which returned a pointer to a stack-resident anonymous slice; its third element (the runtime `command` string) was invalidated before `duplicateArgv` could copy it, so every shell invocation exec'd an empty command and every tool call reported `[noOutputExpected=true]`. Allocate the argv array in the caller's frame instead so the slice outlives the dupe.
- **Fix (data loss)**: `collectWithTimeout` replaced `std.Io.poll` with a direct `posix.poll`+`posix.read` loop. The stdlib Poller skips `read()` when `revents` has `POLLHUP` but not `POLLIN` together on a separate iteration, which on macOS happens for fast-exiting processes — buffered pipe bytes were discarded. The new loop reads whenever either flag is set and only marks the fd closed after `read()` returns 0.
- Strip leaked `{"tool_calls":...}` and `{"assistant":..., "tool_calls":..., "control":{...}}` JSON envelopes from the displayed assistant transcript. Qwen3.x and other local models sometimes echo their own protocol instructions inline; the raw JSON was ending up in the assistant bubble (with escaped heredocs and all) instead of the clean tool-card rendering above. The strip is render-only — full text is kept in history so the model keeps its own context.
- Loop breaker now stops immediately on the first identical-tool-call repeat (previously gave the model another round with tools disabled, which doubled the stall time when the model was already stuck). Hashing was already tool-call-content-only, so a matching signature means the exact same call twice in a row.

- Enterprise hardening pass 106 (D2/D8 — bound JSON parse across all four sites in the local/Ollama provider): `providers/local.zig` had four bare `parseFromSlice(... .{})` sites the pass-105 sweep missed. (a) `parseOllamaStreamChunks` per-line stream parse -- a hostile local provider could ship a 50 MB single-line "chunk" to exhaust parser memory. (b) `isOllamaTruncated` parses the response body just to read `done_reason` -- same attack vector. (c) `extractThinkingField` parses the response body to extract `thinking` / `reasoning_content` -- same. (d) `parseDiscoveredModels` parses the `/api/tags` response -- analog of pass 105's per-provider fix. All four routed through `parse_helpers.parseJsonBounded` (1 MiB-per-value cap). - Enterprise hardening pass 105 (D2/D8 — bound JSON parse of `/v1/models` discovery responses across all five HTTP providers): `parseDiscoveredModels` in `providers/anthropic.zig`, `openai.zig`, `deepseek.zig`, `groq.zig`, and `gemini.zig` each parsed the model-discovery HTTP body via bare `std.json.parseFromSlice(... .{})` -- no `max_value_len`. Routed all five through `parse_helpers.parseJsonBounded` (1 MiB-per-value cap from `json_parse_options`). Closes the model-discovery hop in the JSON-parse bounds sweep that started in pass 103. Smoke harness stays at 184/184 green.
- Enterprise hardening pass 104 (D2/D8 — bound JSON parse of native-tool-call array + tagged-body envelope): pass 103 closed `parseArgumentsField`. Two more entry points on the model-output / provider-response parse path were still using bare `std.json.parseFromSlice(... .{})`: (a) `core/parse_json.zig::parseNativeToolCallsJson` parses the `tool_calls` array directly from a provider's HTTP body (OpenAI-style native function-calling, also used by Anthropic / Gemini adapters that normalize into the same shape) -- a hostile or compromised provider, or a misconfigured base_url pointed at attacker-controlled HTTPS infrastructure (pass 73's egress chokepoint stops plaintext but not a malicious-but-HTTPS upstream), could ship a 50 MB string literal or deeply-nested array designed to exhaust parser memory or blow the stack. (b) `core/parse_blocks.zig::appendTaggedToolCallBody` parses the body of `[tool_call]...[/tool_call]` envelopes from model output text -- same model-controlled risk. Routed both through `parse_helpers.parseJsonBounded`, which pins the 1 MiB-per-value cap from `json_parse_options`. Smoke harness stays at 184/184 green.
- Enterprise hardening pass 103 (D2/D8 — bound JSON parse of model-controlled tool-call argument strings): `core/parse_helpers.zig::parseArgumentsField` is invoked when the agent runtime parses a tool-call envelope and sees an `arguments` / `args` value that's a string -- the function tries to JSON-parse the string and lift its keys into the kv-text args. The previous call used the bare `std.json.parseFromSlice(... .{})` form with no `max_value_len`, so a hostile model could embed a 10 MiB string literal in a tool arg or a deeply-nested structure designed to blow the parser stack (or just allocate gigabytes). Switched to `parseJsonBounded`, which pins the project's standard 1 MiB-per-string/array/object cap (`json_parse_options`) -- well past anything legitimate for tool args and bounds adversarial memory blow-up. The fallback path (parse failure -> dupe the raw string verbatim) still trips the WriteContentTooLarge / args-cap downstream caps. Smoke harness stays at 184/184 green.
- Enterprise hardening pass 102 (D2/D5 — bound provider-call `timeout_ms` to defeat `(ms + 999)` overflow): `providers/common.zig::callHttp` and `callHttpStreaming` did the same `(timeout_ms + 999) / 1000` ceiling-divide pattern that pass 101 fixed in `tools/tool_dispatch.zig`. The `timeout_ms` parameter ultimately carries `provider_timeout_ms` from `config.toml`, parsed as u32. With a hostile or typo'd value of u32::max (~50 days), the bare `+ 999` add overflowed u32 to 998 -- ReleaseFast yielded a 1-second curl timeout instead of the long wait the operator asked for, safe builds panicked. The streaming variant is worse: it had no `@max(1, ...)` safety on the output, so the wrap could even produce a 0-second timeout. Cap both sites at one hour of ms (well within u32 and past anything legitimate for an LLM API call) before the round-up. Smoke harness stays at 184/184 green.
- Enterprise hardening pass 101 (D2/D5 — bound `timeout_ms` parsing to defeat `(ms + 999)` overflow): `tools/tool_dispatch.zig` had two sites doing the standard ceiling-divide-by-1000 pattern (`(parsed + 999) / 1000`) without bounding the input: (a) `msToSecsOrFallback`, used to convert `ZCODE_BASH_DEFAULT_TIMEOUT_MS` / `BASH_MAX_TIMEOUT_MS` env vars from ms to secs; (b) the `timeout_ms` branch of the per-call shell-tool resolver that reads from model-supplied tool args. With `parsed = usize::max` (a hostile/typo'd env var, or an attacker-controlled tool-arg JSON), the `+ 999` add overflows usize -- ReleaseFast wrapped to 998, yielding a 1-second timeout instead of the long-timeout the user asked for, and safe builds panicked. Added a "cap at one year of ms" check before the round-up at both sites. The cap is past anything legitimate, keeps the math entirely inside usize, and removes the overflow surface. Smoke harness stays at 184/184 green.
- Enterprise hardening pass 100 (D2/D5 — bound `created_ts` in cron loader to defeat i64 underflow): `core/cron.zig::loadDurable` reads each persisted entry's `created_ts` from `~/.zcode/scheduled_tasks.json` and computes `now - created_ts` to drop entries older than 7 days. With a hand-edited or malformed JSON setting `created_ts` to i64 min (or i64 max in the far future), the bare subtraction overflowed i64 in ReleaseFast (UB / wrap-around) -- panicking in safe builds, returning a wrap-twisted value otherwise that randomly classified the entry as fresh-or-stale. Same defect family as pass 99 (cron-interval overflow) on the load side. Bound `created_ts` to a +/-100-year window around `now` and use saturating subtraction (`-|`) so even an out-of-window value cannot overflow. Smoke harness stays at 184/184 green.
- Enterprise hardening pass 99 (D2/D5 — clamp pathological cron intervals to bound i64 overflow): `core/cron.zig::computeNextFireTime` parsed the `*/N` minute and hour-interval fields with `parseInt(i64, ...)`, then multiplied by 60 / 3600 to get seconds. A pathological schedule like `*/9223372036854775807 * * * *` (operator-edited `~/.zcode/scheduled_tasks.json`, or a `/schedule` call the user was tricked into) parsed to i64 max; the subsequent `interval * 60` overflowed in ReleaseFast (undefined behavior, observed wrap-around to small/negative values), making `computeNextFireTime` return a time *in the past* and pegging the cron loop firing continuously -- a tight CPU spin from a single bad schedule. Added `std.math.clamp(raw, 1, MAX_INTERVAL_*)` for both the minute (`*/N` -> capped at one year of minutes) and hour (`* */N` -> capped at one year of hours) positions. Both bounds keep the multiplication safely inside i64 and reject anything past a year as nonsensical for an interactive cron. Two new regression tests fire `*/i64_max` at both positions and assert the next-fire-time stays within a year of `now` and is strictly after it. Smoke harness stays at 184/184 green.
- Enterprise hardening pass 98 (D5/D7 — handle `SIGQUIT` in `installInterruptHandlers`): pass 97 hooked `SIGHUP` to the terminal-restore handler, but `SIGQUIT` (Ctrl+\) was still on its default action ("terminate with core dump").
